# Задача 11: Лидерборд игроков

**Студент:** Карпач В.Р.

## Постановка

Топ-K, обновление очков. Тесты: ничья, K больше числа игроков. AI-review: сложность сортировки/структуры данных.

## Что реализовано

Модуль `leaderboard.py` (Python 3.10+, без внешних зависимостей):

- `add_score(nickname, points)` — прибавить очки игроку (целое > 0), игрок создаётся при первом начислении;
- `top(k)` — топ-K игроков (`Entry(rank, player, score)`); `k` больше числа игроков вернёт всех, `k = 0` вернёт пустой список;
- `rank_of(nickname)` — место игрока или `None`;
- `reset()` — очистка таблицы (смена сезона).

Правила: ник нормализуется (без учёта регистра и пробелов по краям), при равенстве очков выше тот, кто набрал их раньше, места уникальны (1, 2, 3, …). Сложность: `add_score` O(1), `top(k)` O(n log k), `rank_of` O(n).

## Работа с ИИ

### Использованные инструменты

Claude (чат-интерфейс claude.ai): генерация кода, генерация тестов, ревью и проверка качества тестов.

### Ключевые промпты

Полный список с итерациями: [docs/prompts.md](docs/prompts.md). Кратко:

1. «Напиши на Python класс `Leaderboard`: обновление очков и топ-K, без внешних библиотек.»
2. «Напиши `unittest`: топ, ничья, K больше числа игроков, накопление очков.»
3. «Проведи ревью кода и тестов: краевые случаи, ввод, детерминированность ничьей, сложность `top(k)`, потокобезопасность. Для каждой находки дай входные данные, на которых код ломается.»
4. «Перепиши модуль с учётом принятых находок, внешних зависимостей не добавляй.»
5. «Какие поломки кода мои тесты не заметят? Внеси их по одной и проверь запуском.»

### Что ИИ сделал хорошо

- Быстро дал рабочий черновик и структуру тестов.
- В ревью указал реальные проблемы с воспроизводимыми примерами: `top(-1)` теряет игрока, `NaN` ломает порядок, ничья зависит от порядка вставки в словарь. Каждая находка подтверждена запуском.

### Что ИИ сделал плохо

- Черновые тесты были «зелёными», но слабыми: один из них закреплял случайный порядок при ничьей, а неверный ввод не проверялся вовсе.
- Первый тест на потоки проходил даже на коде **без** блокировки (ложное чувство безопасности); после усиления он ловит ошибку лишь в 3 из 10 запусков.
- Оценка выигрыша от кучи в ревью была оптимистичной: на 200 000 игроков реальный выигрыш ≈ 2,5× (79,6 мс → 31,8 мс), а не порядки.

### Что исправлено (по итогам ревью)

Валидация `k`, очков и ника; нормализация ника; детерминированная ничья через счётчик обновлений; `top(k)` на `heapq.nsmallest`; `RLock`; метод `rank_of`; тесты переписаны и дополнены. Подробности и измерения: [docs/ai-review.md](docs/ai-review.md).

### Мои ручные правки
После проверки кода и тестов я сам принял следующие решения (часть из них
отклонила предложения ИИ):

- **Отклонил `set_score` (прямое задание очков).** ИИ предлагал метод для
  установки очков «сверху». Я отказался: постановка говорит только про
  «обновление очков», а прямой set ломает правило ничьей (непонятно, когда
  игрок «достиг» счёта). Оставил только `add_score`.
- **Отклонил отрицательные очки для штрафов.** Это сделало бы рейтинг
  немонотонным и потребовало бы отдельного продуктового решения, которого
  в постановке нет. Оставил `points > 0`.
- **Отклонил «конкурентные» места при ничье (1, 2, 2, 4).** Выбрал
  уникальные места 1, 2, 3, …, потому что порядок при ничье у меня всегда
  однозначен (по счётчику обновлений), и так `rank_of` гарантированно
  согласован с `top`. Это моё решение, а не ответ ИИ.
- **Отклонил `time.monotonic()` для ничьей, предложенный ИИ.** В тестах
  пришлось бы патчить часы, а две записи в один «тик» дают
  недетерминированный порядок. Заменил на счётчик обновлений `_reached` —
  детерминирован и проверяется без подмены времени.
- **Сам проверил `heapq.nsmallest` с `key` по словарю.** Не поверил на слово:
  добавил в тесты сверку с «наивной» эталонной сортировкой на 2000 случайных
  обновлениях с фиксированным seed (`test_matches_brute_force_on_random_data`).
- **Сам усилил тест на потоки.** Первая версия теста от ИИ проходила даже
  на коде **без** блокировки — ложное чувство безопасности. Добавил
  `sys.setswitchinterval(1e-6)`, 8 потоков × 2000 обновлений. Честно
  зафиксировал в `docs/ai-review.md`, что тест остаётся вероятностным
  (ловит ошибку в 3 из 10 запусков), а не доказательством.
- **Скорректировал оценку ИИ по производительности.** ИИ утверждал, что куча
  даёт «выигрыш на порядки». Я замерил: на 200 000 игроков реально ≈ 2,5×
  (79,6 мс → 31,8 мс). Записал фактическую цифру, а не оптимистичную оценку.
- **Проверил вручную краевые случаи, которые «зелёные» тесты ИИ не ловили:**
  `top(-1)` (терял игрока в v1), `top(True)`, `NaN` в очках, пустой ник.
  Каждый подтвердил запуском и закрыл тестом.

### Риски и ограничения

- **«Уверенный» неверный код:** черновик выглядел корректно и проходил свои тесты, но терял игроков при `top(-1)`. Зелёные тесты ИИ — не доказательство правильности; нужны собственные краевые проверки и мутационная проверка.
- **Галлюцинации и неверные оценки:** утверждения ИИ о производительности и потокобезопасности проверялись замерами и запуском, а не принимались на веру.
- **Утечки данных:** в промпты отправлялся только код учебного модуля, без персональных данных и секретов.
- **Лицензии:** код короткий и типовой (словарь, куча, блокировка); внешних библиотек и фрагментов чужих репозиториев нет.
- **Зависимость от инструмента:** без понимания кода (кучи, ничьей, блокировок) оценить качество ответа ИИ нельзя.
