# AI-assisted ревью: лидерборд игроков

**Что ревьюилось:** черновик `docs/draft-v1/leaderboard_v1.py` и четыре черновых теста `docs/draft-v1/test_v1.py` (первая версия, полученная от ИИ).
**Фокус ревью (из постановки):** сложность сортировки и структуры данных; плюс краевые случаи, безопасность ввода и тестируемость.
**Метод:** ИИ перечислил подозрительные места, затем **каждая находка проверялась запуском** (пробы на v1, бенчмарк, мутационная проверка тестов). Выводы ниже взяты из фактических запусков, а не из рассуждений.

## Исходный код v1

```python
class Leaderboard:
    def __init__(self):
        self.scores = {}
    def update_score(self, player, points):
        self.scores[player] = self.scores.get(player, 0) + points
    def top(self, k):
        return sorted(self.scores.items(), key=lambda x: x[1], reverse=True)[:k]
```

Все 4 черновых теста v1 проходят (`OK`), то есть формально «зелёные тесты» были, но качество кода это не подтверждает.

## Находки

| № | Находка | Доказательство (запуск на v1) | Решение | Правка в v2 |
|---|---------|-------------------------------|---------|-------------|
| 1 | Отрицательное `k` молча отрезает хвост | `top(-1)` при 3 игроках → `[carol, bob]`, последний игрок потерян без ошибки | Принято | `ValueError` при `k < 0` |
| 2 | Некорректный тип `k` ведёт себя непредсказуемо | `top(True)` → 1 игрок, `top(None)` → все, `top(2.0)` → `TypeError` из недр среза | Принято | явная проверка: не `int` или `bool` → `TypeError` |
| 3 | Очки не валидируются | `True` принимается как 1, `-50` уменьшает очки, `NaN` ломает порядок (`30, 20, 10, nan, 25`), `'5'` даёт невнятный `TypeError` | Принято | только `int > 0`; `bool` и `float` (включая `NaN`) → `TypeError`, `≤ 0` → `ValueError` |
| 4 | Ники не нормализуются | `'Neo'`, `' neo '`, `''` — три разных игрока | Принято | NFKC + `strip` + `casefold`, пустой ник → `ValueError`, показывается первое написание |
| 5 | Порядок при ничьей зависит от порядка вставки в словарь | bob 5 → alice 10 → bob +5: v1 даёт `bob, alice`, хотя 10 очков первой набрала alice | Принято | счётчик обновлений `_reached`; ключ сортировки `(-очки, _reached)` |
| 6 | `top(k)` полностью сортирует всех игроков: O(n log n) на каждый вызов | N = 200 000, K = 10: **79,6 мс** (v1) против **31,8 мс** (v2) | Принято частично | `heapq.nsmallest` даёт O(n log k); выигрыш ≈ 2,5×, а не «на порядки» (см. ниже) |
| 7 | Обновление очков не атомарно | в v1 нет синхронизации; `get` + запись в словарь не атомарны даже под GIL | Принято | `RLock` вокруг всех операций |
| 8 | В v1 нельзя узнать место конкретного игрока | нет такого метода | Принято (расширение) | `rank_of()` — O(n), возвращает `None` для неизвестного игрока |

### Оценка находок (согласие и несогласие)

- **№ 6, согласен лишь частично.** Куча уменьшает сложность выборки, но все n игроков всё равно просматриваются в Python, поэтому реальный выигрыш всего ≈ 2,5×. Для настоящей нагрузки нужна структура, поддерживающая порядок при обновлении (дерево/skip list, `sortedcontainers` или Redis sorted set, как в лабораторной по Docker). Я **не** стал подключать внешнюю библиотеку: для учебного модуля это избыточная зависимость, а ограничение описано в докстринге модуля (`add_score` O(1), `top(k)` O(n log k), `rank_of` O(n)).
- **№ 5, альтернатива отклонена.** Вместо счётчика можно хранить `time.monotonic()`. Я отказался: в тестах время нужно подменять, а две записи в одно «тиковое» значение дают недетерминированный порядок. Счётчик обновлений детерминирован и проверяется без патчинга часов.
- **Отклонённые предложения ИИ:**
  - метод `set_score` (прямое задание очков) — вне постановки («обновление очков» покрыто `add_score`) и усложняет правило ничьей;
  - отрицательные очки для штрафов — делают рейтинг немонотонным; это отдельное продуктовое решение, а не доработка;
  - «конкурентные» места при ничьей (1, 2, 2, 4) — выбраны уникальные места 1, 2, 3, …, так как порядок всегда однозначен и `rank_of` согласован с `top`.

## Ревью тестов

**Черновые тесты v1:**
- проверяют только «счастливый путь», ни одного теста на неверный ввод, `k = 0`, отрицательное `k`;
- `test_tie` проходит **случайно**: он утверждает порядок `alice, bob`, который в v1 получается лишь из-за порядка вставки в словарь. Пример из находки № 5 показывает, что контракт «кто раньше» на нём не держится. Тест фиксирует побочный эффект, а не правило.

**Итоговые тесты (19 штук, `tests/test_leaderboard.py`):** добавлены ничья по моменту набора очков (в том числе пример из находки № 5 и ничья из трёх), `k` > числа игроков, `k = 0`, неверные `k`, очки и ники, Unicode-нормализация, сверка с «наивной» эталонной сортировкой на 2000 случайных обновлениях (seed фиксирован), согласованность `rank_of` и `top`, сброс, параллельные обновления.

**Мутационная проверка** (в код специально вносилась ошибка, тесты должны упасть):

| Внесённая ошибка | Результат |
|------------------|-----------|
| ключ сортировки без момента набора очков | пойман (3 падения) |
| нет проверки отрицательного `k` | пойман |
| ник не нормализуется | пойман (2 падения) |
| `bool` принимается как очки | пойман |
| **убрана блокировка** | **не пойман с первого раза** |

Последний пункт — слабое место, и честно: ИИ написал тест на потоки, который **с первой версии проходил даже на коде без блокировки**, создавая ложное чувство защищённости. После усиления (частое переключение потоков через `sys.setswitchinterval`, 8 потоков × 2000 обновлений) тест ловит ошибку лишь **в 3 из 10 запусков**. Гонки по природе вероятностные, поэтому тест остаётся «сторожем с вероятностью», а не доказательством. Корректный код с блокировкой прошёл все 5 контрольных прогонов. Детерминированная проверка отсутствия гонок потребовала бы другого инструмента (например, анализатора потоков) и выходит за рамки учебной работы.

## Что осталось вне доработок (известные ограничения)

- Данные хранятся только в памяти, без сохранения на диск.
- `rank_of` работает за O(n): для частых запросов места нужна другая структура.
- Отображается первое написание ника: «Neo» не превратится в «NEO», даже если игрок начислит очки под другим регистром.
- Тест на потоки вероятностный (см. выше).
